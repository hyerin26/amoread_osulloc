## 0. 전제와 가정

### 0.1 확정된 방향 (사용자 결정, 2026-11-05)
- AMOREAD는 기존 툴의 업무 흐름까지 포함하는 **단일 툴**이다.
- 할인 기획과 페이지 기획은 **같은 담당자(멘토님)**가 하며, **무엇을 먼저 할지는 매번 다르다.**
- 기획은 대개 **명분(왜 지금) → 컨셉 도출**에서 시작한다.
- 팀이 가장 공들일 영역은 **페이지 기획**이다. 명분 캘린더도 사용성을 개선하고 명분 잡기를 돕는다.
- 캘린더에서 시작하지 않고 **브리프에서 바로 시작한 기획도 캘린더에 반영**한다.

### 0.2 인터뷰 전 임시 가정
| ID | 가정 | 검증 질문 |
|---|---|---|
| H-1 | 기획안 1개 = 명분 1개 + 기간 + 할인 행 0~n개 + 페이지 0~1개. 페이지 트랙은 선택 | A1, A2, A3 |
| H-2 | AMOREAD의 상품 단위 `sku`는 기존 툴의 **SEQ**(몰 판매 단위)에 대응 | D4, 실데이터 확인 |
| H-3 | PROMO_WORK(공유 xlsm)가 운영 가격의 기준값이다. 툴은 **읽기만** 한다 | D1 |
| H-4 | 1인 로컬 도구로 시작한다(127.0.0.1, 기획자 PC). 공유 저장·다중 사용자는 이후 과제 | F2, B4 |
| H-5 | 할인 외 혜택(쿠폰·사은품 등)은 기존 데이터에 없으므로 기획안에서 **직접 입력** | D2 |

### 0.3 절대 원칙
1. **멘토님 원본 폴더는 수정하지 않는다.** 모든 개발은 별도 작업 복사본에서 한다.
2. **원천 데이터는 읽기만 한다.** PROMO_WORK, SEQ_MASTER, 온라인 가이드, 실적 CSV가 대상이다. 공유 xlsm에 쓰는 기능은 만들지 않는다.
3. **운영계 쓰기와 양방향 동기화는 별도 승인 전까지 만들지 않는다.**
4. 실데이터, 원가, 고객정보를 외부 서비스로 보내지 않는다. AI 연동은 승인 후(Phase 9) 진행한다.
5. 각 Phase 시작 전에 승인 게이트(G0~G9)를 둔다. 패키지 설치, 툴 실행, 소스 반입은 게이트에서 별도로 승인받는다.

## 2. 기술 기반 결정

### 2.1 비교
| 안 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 기존 서버 확장 (추천)** | 기존 FastAPI 서버 복사본에 AMOREAD 백엔드 모듈과 화면을 추가 | 원천 읽기·계산 엔진·보안 미들웨어·기획안 저장을 그대로 재사용. 새 패키지 설치 없음 | AMOREAD 화면을 CSP 규칙에 맞게 고쳐야 함 |
| B. 두 앱 병행 | AMOREAD 단일 HTML을 유지하고, 기존 서버를 API로만 호출 | AMOREAD 코드 변경이 적음 | 두 앱 사이 인증 토큰·CORS 문제. 사용자가 두 화면을 오감 |
| C. 새로 작성 | 새 스택으로 전부 재작성 | 구조 자유도 | 공수가 가장 큼. 기존 검증 로직을 다시 만들어야 함 |

**추천 근거 [사실]**
- 기존 툴은 원천 파일 읽기(`sources.py`, `ops/core/promo_workbook.py`), 숫자 계산(`engine.py`), 기획안 저장(`plans.py`), 보안 미들웨어(`server.py Guard`)를 이미 갖추고 있다.
- AMOREAD 오프라인본은 브라우저 저장공간(localStorage)만 쓰는 단일 HTML이다(`00_사내노트북_시작하기.md`). 실데이터 연동과 서버 저장이 불가능하다.

### 2.2 기술 제약 [사실]
- 기존 서버의 CSP는 `script-src 'self'; style-src 'self'`이다(`server.py Guard`).
  - **인라인 `<script>`·`<style>`, HTML `style="..."` 속성, `onclick=` 같은 인라인 핸들러가 막힌다.**
  - AMOREAD는 4개 소스를 하나의 `index.html`로 합치는 방식이다(`scripts/build.py`). 그대로는 동작하지 않으므로 **JS·CSS를 별도 파일로 분리**해야 한다.
  - 기존 툴 규칙: "HTML `style=` 속성 대신 CSS 클래스·CSSOM 사용"(README_멘티용.md)
- 화면은 프레임워크 없는 ES 모듈(`static/js/*.js`)이다. 공통 유틸은 `core.js`의 `api`, `emit/on` 이벤트 버스, `openModal/openSheet`, `esc`이고, 라우팅은 `app.js`의 `go(view)`이다.
- 기존 venv는 Python 3.15로 실행된 흔적이 있다(`__pycache__/*.cpython-315.pyc`). README의 최소 요구는 3.11+이다.

### 2.3 신규 의존성
- **추가 패키지 없음**을 목표로 한다.
  - 테스트는 Python 표준 `unittest`를 쓴다.
  - PDF는 브라우저 인쇄 CSS(`@page { size: A4 landscape }`)로 만든다.
- AI 기능을 쓰지 않는 단계에서는 `claude-agent-sdk` 설치를 빼는 최소 requirements를 검토한다(G0에서 결정).

### 4.2 매핑 규칙
| 통합 기획안 | 기존 툴 | AMOREAD 문서 계약 | 비고 |
|---|---|---|---|
| `brief.myeongbun/concept/customer/target` | `brief_meta.*` [사실] | Project.brief | 그대로 옮김 |
| `brief.purpose/audience/background/constraints` | 없음 | S03 브리프 [사실: 기능정의서 S03 "기간·목표·타깃·제약"] | 신규 |
| `brief.period` | **없음** [사실: 기획안 기간은 행 날짜에만 있음] | Project.period | 신규 필드. 캘린더 역반영의 핵심 |
| `promo_rows[]` | `rows[]` (`engine.PLAN_ROW_FIELDS`) [사실] | — | `engine.check_plan` 그대로 사용 |
| `page.sections[].zone_tag` | `category_tag` = PROMO_WORK 카테고리명(Zone) [사실] | Section | 섹션과 Zone을 잇는 연결 키 |
| `slots[].seq` | SEQ [사실] | ProductSlot.sku | [H-2] |
| `slots[].items` (seq=null) | 신규조합 `items[{seq,qty}]` [사실] | 신규 묶음(미확정 카드) | 문서 O-07과 같은 개념 |
| 가격 | `promo_rows[].rate` + PROMO_WORK 할인율·할인가 | ProjectPrice / PriceDraft | 4.3 참조 |

### 4.3 가격 데이터 단일화 규칙 [제안 · 결정 필요 DI-3]
가격은 세 겹으로 구분해 보여준다.

| 겹 | 출처 | 편집 | 표시 |
|---|---|---|---|
| ① 운영 기준값 | PROMO_WORK 할인율·할인가 (데이터 갱신 시점의 스냅샷) | 불가 | "운영 기준 · 갱신 MM/DD" 라벨 |
| ② 기획안 값 | `promo_rows[].rate` (할인율 정율 기준), 할인가는 `engine.sale_price`로 계산 | 가능 (할인 트랙·구좌 편집 어디서든 **같은 값**) | 기본 표시 |
| ③ 편집 중 초안 | 화면 상태 (AMOREAD PriceDraft) | `가격 적용` 전까지 임시 | "미적용" 표시 |

- AMOREAD 오프라인본의 독자 가격 저장소(`priceBySku`)를 두지 않는다. **구좌 편집의 가격 적용은 같은 기획안의 `promo_rows` 할인율을 바꾼다.** 이렇게 해야 할인 트랙과 페이지 트랙의 숫자가 갈라지지 않는다.
- 구좌에 연결한 상품이 `promo_rows`에 없으면 "할인 행으로 추가할까요?"를 묻고, 유형·기간을 받아 행을 만든다.
- ①과 ②가 다르면 배지로 표시한다. **①을 덮어쓰는 기능은 없다.**
- 판매가 직접 입력 시 할인율을 역산한다(AMOREAD D-022). 할인가는 기존 엔진처럼 반올림 정수로 계산한다(`engine.sale_price`). 원단위 정책은 Q-D1로 확인한다.

## 5. 화면 구조(IA)와 주요 흐름 [제안]

- 기존 v5 개편안에서 빼기로 한 SAP 실적 KPI·D-day 표는 일단 근거 메뉴로 옮기고, 인터뷰(G1, F3) 후 정리한다.

### 5.3 흐름 1: 캘린더에서 시작
1. C1에서 명분을 클릭하면 C2 카드가 열린다. 카드에는 D-day, 준비 시작일, 씨앗, 작년 같은 명분 행사의 성과, 이미 잡힌 행사, 최근 쓴 컨셉이 보인다.
2. `[이 명분으로 기획 시작]` → B1이 미리 채워진다.
   - 명분 ← 이름
   - 기간 ← 명분 날짜·종료일 (기획자가 수정)
   - 컨셉 후보 ← 씨앗(`|`로 나뉜 값을 칩으로 보여주고 하나를 고름)
   - 페이지 유형 ← `기획일정_구분.csv` 규칙
   - origin = calendar
3. 저장하면 H1으로 이동한다. 캘린더에는 '내 기획안 · 기획 중'으로 표시된다.

### 5.4 흐름 2: 브리프에서 바로 시작 (캘린더 역반영)
1. L1 또는 상단 `[+ 새 기획]` → 빈 B1 (origin = brief)
2. 명분·기간을 입력한다. 기간을 비워 두면 '날짜 미정'으로 저장된다.
3. 저장 직전에 **캘린더 반영 미리보기**를 보여준다. ("12/1~12/25 '내 기획안' 겹에 표시됩니다")
   - 체크박스: `이 명분을 명분 사전에도 추가` (기본 해제, DI-5)
   - 체크하면 종류(8종)와 준비 기간(일)을 입력받는다. `schedule.save_seasons`의 검증을 그대로 쓴다.
   - 같은 이름과 날짜의 명분이 이미 있으면 추가하지 않고 연결만 한다.
4. 기간이 없는 기획안은 C1 옆 '날짜 미정' 보관함에 보인다. 끌어서 날짜에 놓으면 기간이 정해진다(P1).
5. 브리프의 기간·명분을 바꾸면 캘린더 표시도 함께 바뀐다. 기획안이 원본이므로 다시 입력할 필요가 없다.
   - 명분 사전에 추가한 항목은 별도 사본이므로 자동으로 바뀌지 않는다. 다르면 안내만 한다.

### 5.5 흐름 3: 할인 트랙과 페이지 트랙 오가기
- 허브 탭은 순서와 무관하게 언제든 이동할 수 있다. 각 탭에 상태를 표시한다(`비어 있음 / 작성 중 / 확인할 것 N`).
- **할인 → 페이지:** `[Zone으로 섹션 초안 만들기]`
  - `category_tag`별로 섹션 1개를 만들고, Zone 안 상품을 슬롯으로 연결한다.
  - 하루특가 행은 '날짜별 교체 배너' 섹션 1개로 묶는다. 기존 `designerText` 규칙과 같다.
  - 이미 섹션이 있으면 새로 만들지 않고 **차이만 제안**한다. 사용자가 편집한 카피·순서는 덮어쓰지 않는다(AMOREAD 원칙).
- **페이지 → 할인:** 구좌에 상품을 연결하거나 가격을 적용하면 `promo_rows`에 행이 추가·수정된다(4.3). 할인 탭에는 "페이지에서 추가됨" 표시가 붙는다.
- 섹션에 Zone 이름을 지정하면 그 섹션 상품 행의 `category_tag`도 맞춰진다. 이 값은 PROMO_WORK 엑셀 '카테고리명' 열로 나간다.

### 5.6 흐름 4: 확인·전달
1. **확인할 것**: 오류 먼저 보여준다.
   - `check_plan`의 오류·주의: 원가율, 겹침, 재특가 간격, 효능 표현
   - 페이지 미확정: 상품·이미지·가격·카피 (AMOREAD F-07-05)
   - 브리프·할인 행 기간 불일치
2. **출력**
   - 디자이너 기획안 PDF: S07 연속 와이어프레임 + 구좌 옆 요청사항. A4 가로. 원가 제외
   - PROMO_WORK 붙여넣기 엑셀: 기존 `plans.export_plan` 재사용. '기획 메모' 시트에 브리프 포함
   - 팀 공유 요약 / 디자이너 브리프 텍스트: 기존 `shareText`·`designerText`를 섹션 기준으로 개선
3. **상태 전이**: `기획 중` → `[확정]`(기존 예측 스냅샷) → 데이터 갱신 후 PROMO_WORK에서 같은 키가 발견되면 `PROMO_WORK 반영됨` 후보로 표시하고, 기획자가 확인한다(Q-F1 전까지 임시 키).
